# 如何让用户参与设计

用户负责表达偏好与关键取舍。代理负责研究、创意与实现。终端对话中，每次只提出一个会改变后续工作的问题，不要求用户先选择模式、填写表单或掌握术语。

## 在改动前做判断

同时考虑影响范围（某个元素、某段内容、整个网站）、偏好（明确、部分明确、不明确）、实现风险（成熟、需试验、效果或成本不确定）。把用户之前说过的话当成已经做出的选择。

- **先对齐方向。** 从零设计且方向未知、参考的审美含义有明显歧义、多个参考在全局上冲突，或确实存在体验不同的路线时，给出一个推荐，必要时再给一个备选。高影响而偏好不明确时，必须等用户回应。
- **先对齐变更。** 拟重新构思首屏、更换整体主题、删除或显著改变核心元素、引入左右整体叙事的复杂交互、或关键素材缺失会迫使方案改向时，说明影响和建议，再确认。已明确要求或确认的同一变化直接执行。局部动效请求本身不授权改造原站。
- **先试技术。** 偏好已经明确而实现风险高，可以直接在独立预览中验证一个关键机制；若技术结果改变叙事、素材成本或交互强度，展示实际原型，再决定是否推广。技术不确定不需要用户替工程师选库。
- **直接做。** 明确喜欢的具体特征、局部样式、响应式、间距、对齐、低风险技术选择、已有素材、不影响正式页面的试验、截图检查和已定方案内的实现与迭代均可自主推进。
- **用户授权代理选择。** “直接做”“你来决定”可减少方向确认。在授权范围内简述采用的假设并推进；保留用户明示的约束。若新发现会突破约束，带着解决建议再问。沉默不等于确认。

## 首屏构图由谁决定

当整体体验方向已经确认，但首屏主角、空间分配或交互入口仍有重大取舍时，先在 CLI 用等宽代码块展示 1–2 个 ASCII 草图。每张标出主体、辅助内容和入口的位置，用一句话描述首次进入或操作时什么会变化；静态方案说明为什么保持静止。推荐一个方案，问一个具体取舍，等待用户选择或修改，再动手做视觉原型。例如，用户选了“按位置探索”，仍应确认播放器常驻还是选点后展开。

草图选择只授权制作关键区域预览。把原型在浏览器里实际看到的画面或可操作入口交给用户，说明观察到的差异，等首屏获确认再扩展正式网站。若不满意，只改原型并复看。构图已明确批准时不重复问草图；只有用户明确将相应决定交给代理，才能在该授权范围内代选，并把决定记为代理选择。局部修复、低风险细节和与首屏构图无关的任务直接执行。

## 让选择可见

把提议放到实际的浏览时刻。例如：“我建议让笔记里的三段录音先分散在时间线上，往下滚时合成一页采访稿。访客第一眼就能理解整理过程。你想先看到这个过程，还是先读整理好的稿子？” 用户可以选 A、合并两个方向，或用自己的话描述。将回答翻译为页面中的可观察变化。

对“太花了”先定位原因：是运动太快、信息太密，还是主体被装饰盖住？如果上下文已说明原因，直接修正。若用户更喜欢旧版，把同一屏的前后画面对照，优先恢复被削弱的构图或动作，只保留有价值的增量。不要仅靠换色重复原提案。

涉及复杂 3D 或关键视觉叙事时，可分两次对齐：先确认方向，再用可操作原型判断节奏、空间感或可读性，最后铺开。没有重大首屏取舍的普通页面和局部简单动效直接实现并在浏览器验收。方向未定且一句具体的画面描述足以让用户选择时，先提问；无需为了提出第一个问题而搭建页面或调用额外的可视化工具。
