# 从已验证的页面建立项目设计规范

进入此阶段需要两项依据：用户已选定视觉方向；关键画面或核心操作已经在实际渲染中验证。记下对应的页面、状态和验证结果。方向未定时继续探索，关键画面未能渲染时保留待验收状态。成熟项目可使用已有、仍获认可的页面作为依据，无须重做一份原型。

## 从项目已有的东西开始

找到实际生效的主题、样式变量、公共组件、导航结构、动效工具与文档；查看它们在代表性页面和窄屏中的用法。标出哪些规则已稳定、哪些只属于某一页、哪里确有缺口。优先引用已有规范和实现。已有品牌构图或核心体验需要改变时，先提供可比较的方案，按交互规则取得确认。局部增强只补本次涉及的差异。

把规范写入目标项目已有的设计文档；若没有合适位置，在项目文档目录建立一份简短的设计规范，例如 `docs/design-system.md`。注明参考画面或路由，以及实现文件与组件名称。只记录这个项目已验证、后续开发者能够执行的决定。

## 规范必须回答的四组问题

| 范围 | 用项目里的具体选择回答 |
| --- | --- |
| **Visual Language** | 哪个产品内容成为焦点？说明页面宽度、网格、对齐、主次比例和窄屏重排；定义标题、正文、注释的层级与换行，色彩的语义和对比。为图片、音频、视频或 3D 指定用途、比例、加载与缺失时的替代。区分跨页共有的语言与单页独有的构图。 |
| **Component System** | 明确公共组件的用途、结构、变体及调用位置。针对实际操作定义默认、选中、悬停、键盘焦点、按下、禁用等相关状态。对会取数或提交的组件补上加载、空、错误和重试的反馈；说明触屏对应操作，以及状态是否应跨页面保留。 |
| **Motion Language** | 哪个动作说明了什么变化？记录触发方式、作用元素、经过验证的时长与缓动、结束或中断方式。说明重复操作和系统减弱动态偏好如何处理。静态布局已能表达层级时，明确哪些区域保持静止。 |
| **UX Principles** | 按用户的主要任务写出入口、导航、当前位置、返回路径和完成反馈。明确键盘与触屏操作、焦点去向、失败恢复，以及窄屏下仍需优先呈现的内容。例如声音档案要明确切换地点是否打断播放，关闭详情后焦点回到哪里。 |

对每项重要规则给出“适用场景 → 可观察的行为 → 代码落点”。例如，若地图标记与地点目录共同表示当前选择，二者应绑定同一个地点 ID；在两种入口分别选择地点，另一处应同步更新。相同的点选颜色不足以保证这项体验一致。

## 将规则落实为代码

- 优先沿用项目的 CSS 自定义属性、主题对象、已有设计 Token 或组件变体。用语义名称表达用途，例如选中标记色、键盘焦点色、详情展开时长。具体值来自已验证画面，规范文档引用代码位置，避免手抄两套数值。
- 把反复出现的结构和状态落实到真实组件、共享样式或已有状态逻辑，并在当前页面实际使用。对简单静态站，原生元素和一份共享样式即可；只在一页使用的特殊构图可以留在页面内。沿用现有技术栈，无须安装新的组件库或 Token 工具。
- 后续页面从已有主题和组件入口开始。公共语义、导航习惯、焦点和反馈应一致；页面可按产品内容改变主视觉、阅读顺序、版式和运动方式。为例外记录具体任务和理由，能在页面局部解决的差异留在局部。

## 检查与维护

打开新增或修改的页面及一个已有代表页面，在相同视口对照截图。检查共同的字体角色、对齐方式、组件状态和素材处理，同时判断各页的主次是否适合自己的任务。实际走通导航、返回、键盘、触屏和相关异常状态，确认视觉提示与真实行为一致。

发现偏差时，先区分实现漂移、合理的单页差异和共用规范缺口。前者修代码；局部差异说明理由；只有被更多场景验证的规则才写回系统。改动公共 Token、组件或行为时，同步更新项目文档，在使用它们的页面复测，并以渲染前后的差异解释修改效果。
